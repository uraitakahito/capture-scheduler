Windmill は Web の管理画面を同梱している。この配備ではそれがそのまま
capture-scheduler の管理画面になる。別に何かを立てる必要はない。

スクリーンショットは全部この repo の実データ（今日の失敗 → 成功の run 履歴）で、
`scripts/docs-shots.ts` が撮った生成物。手で撮った絵は 1 枚も無い ——
スクリーンショットは UI の書き写しで、書き写しは腐るため。撮り直しの手順は
[開発](/development/) を見ること。

## 開き方

```
http://127.0.0.1:8000
```

|          | 既定                 | 上書き              |
| -------- | -------------------- | ------------------- |
| email    | `admin@windmill.dev` | `WINDMILL_EMAIL`    |
| password | `changeme`           | `WINDMILL_PASSWORD` |

## 失敗を掘る —— 実例 1 つ

失敗は段ごとに違う場所で違う理由で起きる。**Runs で段と error を見て、
中身は各サービスのログへ** というのが掘り方。

**`report_level` が capture-ledger の `POST /api/crawls/…/pages` に届かなかった**
（`Unable to connect`・`ConnectionRefused`）。Runs が言うのはここまで —— どの段が・どの宛先に
（`path` の `http://127.0.0.1:9/…`）・何で落ちたか。宛先が API ではないので、原因は
`u/admin/waggle_api_url` の値の側に在る（この絵は、変数をわざと閉じたポートに向けて撮った）。
宛先に届いたうえで `500` などを受け取ったなら、**中身は capture-ledger のログにしか無い**。
UI で分かるのは「どの段が・どの宛先に・何で落ちたか」で、原因の特定は宛先側に渡す、という切り分けになる。

<Image
  src={errReport}
  alt="report_level の失敗 run。Result に Unable to connect（ConnectionRefused、path は http://127.0.0.1:9/api/crawls/…/pages）"
/>

`crawl_host` の失敗も同じ読み方をする。段ごと落ちるのは BrowserHive に 1 つも届かない
ときだけ（`BrowserHive に届きません: …` にエンドポイントが全部並ぶ）。1 つの BrowserHive に断られた
（`400 ValidationException: …`、断られた項目つき）のは段の結果の中のそのページの失敗で、
クロールは続く。どちらでも、BrowserHive がその要求をどう扱ったかは BrowserHive のログに在る。

## Flow と script —— 何をするものか

`f/waggle/crawl_level` を開くと、flow の**説明**（capture-ledger が投げた 1 段を
処理して報告する / **1 段で終わる** / 礼儀の 3 点 / per-key concurrency は CE では
効かない）と、受け取る引数が読める。ここに書いてある思想は
[リンクを辿る](/crawl/) と [Windmill CE](/windmill-ce/) の裏付けそのもの。

<Image src={flowDetail} alt="crawl_level flow の詳細。説明文と Crawl Id・Depth・Frontier の入力" />

flow が for-loop で各 host に対して呼ぶのが `crawl_host` の script。
「1 ホストぶんを逐次で取り込む」「単体で叩くものではない」と説明にある通り、
**flow の部品**で、単独で起こすものではない。

<Image src={scriptForm} alt="crawl_host の script 詳細。flow の部品である旨の説明と入力仕様" />

script のコードは UI の Edit でも repo の `windmill/f/waggle/` でも読めるが、
**正は repo**。UI で直すと次の `windmill:push` で戻る。

## Schedules —— 空のまま

この repo に schedule は無いので、この画面は空のまま。定期実行の時計は
[capture-ledger](https://uraitakahito.github.io/capture-ledger/ja/schedules/) の中に在る。予定を作るのは
[capture-workbench](https://github.com/uraitakahito/capture-workbench) の「新しいクロール」の画面で、
操作はタブ「定期実行」から。

**ここに行が在れば、それは消し残し**で、capture-ledger の予定と別にクロールを始めうる。古い checkout の
`windmill:push` が戻すことがある。`pnpm run doctor` の `schedule` がそれを言い、いまの repo から
`windmill:push` を打てば消える。

## 手で 1 本撮る

ここからは撮らない —— クロールを始めるのは capture-ledger。capture-workbench の「新しいクロール」の画面か、
`pnpm run smoke` を使う（[クイックスタート](/quickstart/#確かめる--1-本撮れるまで)）。この UI の Run のフォームは、
単独で動く script のためのもの —— [落とした物を Windmill で調べる](/inspect/) の script など。

**schema の `default` は UI からの実行にしか埋まらない**（CE の罠。
[Windmill CE](/windmill-ce/) を見ること）。webhook からの実行には届かないので、
flow の script は設定を変数から読む（[リンクを辿る](/crawl/)）。

## 変数の一覧 —— どの script が何を入れるか

`windmill:push` が入れるのは **git にあるものだけ**（script・flow）。
変数は別の script が入れる。ここを混同すると、push が緑なのに flow が最初の
`getVariable` で落ちる。

| 置き場                          | 中身                                                                                                                                                                                           | 入れる script                                                                    |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `u/admin/ledger_client`         | capture-ledger に名乗る flow の app client の JSON (secret)。`issuer`・`tokenUrl`（コンテナから見た宛先）・`hostTokenUrl`・`clientId`・`clientSecret`・`scope`。段ごとに、これでトークンを取る | `windmill:capture-ledger-token`。capture-ledger の `.dev/idp.env` から           |
| `u/admin/waggle_api_url`        | capture-ledger API の宛先（既定は default ネットワークの gateway）                                                                                                                             | 同上                                                                             |
| `u/admin/browserhive_endpoints` | BrowserHive の URL の JSON 配列。BrowserHive 1 つに 1 要素（既定 `["http://browserhive-1.capture-ledger:50051","http://browserhive-2.capture-ledger:50051"]`）                                 | 同上                                                                             |
| `u/admin/browserhive_tls_ca`    | `https://` のエンドポイントのための CA（空 = 平文の `http://`）                                                                                                                                | 同上                                                                             |
| `u/admin/ts_compile_url`        | ts-compile-service の宛先（既定 `http://ts-compile.capture-scheduler:8080`）                                                                                                                   | 同上                                                                             |
| `f/waggle_secrets/<名前>`       | スクリプトが `catalog.json` の `params` で宣言したシークレット (secret)。`crawl_host` が解いて BrowserHive にだけ渡す（[リンクを辿る](/crawl/)）                                               | **人が置く**（`pnpm run windmill:cli variable add`）。フォルダは `windmill:push` |

エンドポイントは BrowserHive v12 から `http(s)://` の URL。`crawl_host` は v11 の `host:port` の形を
この変数の名前を挙げて断り、`windmill:capture-ledger-token` は変数に書く前に断る ——
`.env` に残った古い `CAPTURE_LEDGER_BROWSERHIVE_ENDPOINTS` は flow ではなく道具で止まる。

## 全部消えたときの復旧

windmill-db の volume を消すと、workspace・token・変数が全部消える。
復旧の順序（2026-09-11 に実測）:

```sh
pnpm run windmill:bootstrap            # workspace を作り直し、新しい token を .env.local に、
                                       # capture-ledger に渡す行を .dev/capture-ledger.env に書く
pnpm run windmill:push                 # script / flow
pnpm run windmill:capture-ledger-token # 上の表の変数
cd ../capture-ledger
pnpm run connect                       # 渡す行を取りに行く。そのあと API を起こし直す
pnpm run idp:grant                     # windmill の app client に acme のクロールを許可する
```

capture-ledger 側の OpenFGA も同時に消えていたら、許可を書く前に
`fga:migrate` → `fga:deploy` で store を作り直し、出てきた 2 つの ID を
あちらの `.env` に貼る。capture-ledger で Amazon Cognito の代わりを務める
[Floci](https://github.com/floci-io/floci) のプールも消えていたら（コンテナが作り直されたら）、最後の行の代わりに、
`connect` の後で向こうの `pnpm run dev:up --from idp` を打つ。IdP（identity provider）を用意し直し、API を
起こし直し、許可を与え、`windmill:capture-ledger-token` をやり直す。

**コンテナを作り直すと bridge の subnet が変わりうる。** `u/admin/waggle_api_url` に入るのは、
`windmill:capture-ledger-token` を叩いた時点の default ネットワークの gateway なので、subnet が
変わったらやり直す。外れていると report の段が届かずに落ち（`Unable to connect. Is the computer
able to access the url?`）、クロールは `running` のまま残る。届いているかは `pnpm run doctor` の
container→api が見る —— 変数の宛先の `/healthz` に、worker の中から問い合わせ、届かなければ
宛先をいまの gateway と比べて、古いのか API が 127.0.0.1 で待っているのかを言う。最後に
`pnpm run doctor` が全部 ✓ になり、`pnpm run smoke` が「撮れた」と言えば、復旧は終わり。

## `f/waggle/` という名前

repo は waggle → capture-ledger と改名したが、Windmill の folder は
`f/waggle/` のまま。**folder のパスは webhook URL の一部**
（`/api/w/crawler/jobs/run/f/f/waggle/crawl_level`）で、変えると
capture-ledger 側に設定した webhook が壊れる。名前ではなく外部契約として
据え置いてある。
