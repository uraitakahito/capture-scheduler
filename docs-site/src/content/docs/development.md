## Changing things

Whatever you touch in the Windmill UI has to come back to git.

```sh
pnpm run windmill:diff   # what differs between the UI and git (does not push)
pnpm run windmill:pull   # take the UI's changes into git
pnpm run windmill:push   # make git authoritative and apply it
```

**Both directions delete.** `push` removes remote items that are absent locally;
`pull` removes local files that are absent remotely. Commit before syncing and
push before pulling — see [Windmill CE](/windmill-ce/).

`windmill/wmill.yaml` keeps `includeSchedules: true` although this repository holds no schedule: with
schedules out of the sync, `windmill:push` would not remove one made in the UI or pushed earlier. An old
checkout's `windmill:push` can bring one back, and it would start crawls apart from capture-ledger's
schedules, so doctor's `schedule` line checks that none is left. Secrets are not synced
(`skipSecrets`); `u/admin/waggle_token` is injected through the API by
`scripts/capture-ledger-token.ts`.

Folders are synced (`skipFolders` is not set, so the default applies). `windmill/f/<name>/folder.meta.yaml`
is the source of truth, and **a folder absent locally is deleted by push** — one created through the
API or the UI disappears on the next push (confirmed with `windmill:diff` on 2026-11-01). The folder for
script secrets, `f/waggle_secrets`, is made that way. The variables inside it are not synced, so a push
neither removes nor adds them ([Following links](/crawl/)). A new folder shows up in `windmill:diff` once
more after its first push, as `~ folder` — Windmill adds the creator to `owners` and `extra_perms` when it
creates the folder, which differs from the local `owners: []` (measured with `f/waggle_secrets`). The next
push is expected to write the local shape; `f/waggle` has `owners: []` on the remote too. The "push" line of
doctor compares script contents only, so this difference does not turn it ✗.

When you change the arguments of a script's `main`, regenerate its `.script.yaml` (schema),
`.script.lock` and `wmill-lock.yaml` with `pnpm run windmill:metadata` (`wmill generate-metadata`) and run
`pnpm run format` afterwards (the output is not in prettier's shape). The generator may count scripts
you did not touch as "stale" and rewrite them too — its staleness hash covers the yaml's formatting, so
after `format` everything is stale. You need not commit the regenerated files of scripts you did not
touch; push only warns about stale metadata, it does not stop. `pnpm run windmill:cli <wmill arguments>`
runs any other `wmill` command (`variable add`, for one) against the connection in `.env`.

## Re-taking the screenshots

The PNGs on [The UI](/windmill-ui/) are generated by `scripts/docs-shots.ts` —
none are taken by hand. Re-take them when the UI changes (i.e. when you bump
the Windmill pin in `docker-compose.yml`). `check-doc-refs` fails when the
compose pin and the version in `shots-manifest.json` disagree, so CI stops you
if you forget.

```sh
# 1. Bring the stack up and create the run history the script needs (two of them):
./setup.sh && container-compose up -d -b   # + the capture-ledger API / issuer
#    - one successful crawl_level
#    - one failed report_level (any failure)
# 2. Capture (Chromium is fetched by hand the first time; puppeteer is docs-only)
./node_modules/.bin/puppeteer browsers install chrome
pnpm run docs:shots
```

When you drop `puppeteer`, drop its `//devDependencies` note in `package.json` too.

## Layout

| path                                           | what                                                                                     |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `windmill/f/waggle/*.ts`                       | the scripts Windmill runs, under Bun                                                     |
| `windmill/f/waggle/crawl_level.flow/flow.yaml` | the flow that runs one crawl level                                                       |
| `windmill/f/waggle_secrets/folder.meta.yaml`   | the folder for script secrets; the variables inside are placed by a person, never in git |
| `test/`                                        | unit tests; **never put these under `windmill/f/`** — `sync push` would deploy them      |
| `scripts/*.ts`                                 | host-side helpers (bootstrap, tokens, checks)                                            |
| `.env.local`                                   | **written by the tools** (`WINDMILL_TOKEN`); git ignores it                              |
| `.dev/capture-ledger.env`                      | the lines for capture-ledger. **Its `pnpm run connect` reads them**                      |

Adding an environment variable is a three-part contract, checked in both
directions by `scripts/check-env.ts`: `.env.example`, the name lists in
`scripts/env.ts`, and a literal-string read.

### There are two settings files

Every runnable script hands node `.env` and then `.env.local` (two
`--env-file-if-exists` flags). **The later one wins**, so a name present in both
takes its value from `.env.local`.

They are split because they have different owners. `.env` holds what a person
decided; `.env.local` holds **what only running things can decide** (the Windmill
token). When a tool reorders or drops a line a person wrote, nobody can tell
afterwards what happened.

**Write only inside your own repo; to cross, read.** `windmill:bootstrap` is a
command you run in capture-scheduler, so it never writes into capture-ledger —
the lines for capture-ledger go into `.dev/capture-ledger.env`, and fetching them is the other
side's `pnpm run connect`. A repo changing because of a command typed somewhere
else is not what the person typing it expects.

When you suspect a stale `.env.local`, the fastest fix is to **regenerate both**:
run `pnpm run windmill:bootstrap` again, then `pnpm run connect` in
capture-ledger. Both are safe to repeat (tokens accumulate, and the old ones
stay valid).

## Out of scope

1. **Nobody is told when it fails.** A failed run of the flow leaves a red entry in
   the run history and waits to be noticed. A scheduled run that fails also shows in
   [capture-workbench](https://github.com/uraitakahito/capture-workbench), on a band
   across its views; nothing sends it anywhere.
2. **No production topology is decided.** Apple Container is for development.
